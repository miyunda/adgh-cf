# 通用 HTTPS 默认模式与域名组

设计日期：2026-10-10，状态更新：2026-10-11（北京时间）。本文为设计与验收依据；格式 2 已实现，家庭 Linux 正常切换已实测，故障恢复真机实测延期，完整验收待完成。当前记录见 [STATUS.md](../STATUS.md)，使用与迁移见 [DOMAIN-GROUPS.md](../DOMAIN-GROUPS.md)；下表“当前行为”保留设计时的旧单域名基线。

## 目标与范围

将服务对象从家庭 OpenBao 用户扩展到需要改善 Cloudflare 网站直连体验的用户：提供一个普通 HTTPS URL 即可只读测速；需要自动更新时仍使用现有 AdGuard Home。OpenBao 是保留的专用探测模式，不再是新配置的默认模式。

本阶段仍限定 Cloudflare 常规 CDN 公网 IPv4、HTTPS 443、实际使用出口上的测量。通用 HTTPS 判断不意味着任意网站都可以指向 Cloudflare IP，也不承诺所有组员都达到各自最快速度。保留 Host/SNI、证书验证、直连测速、有限请求、连续确认和冷却机制。不增加依赖、GUI、带宽测试、HTTP/2/3、认证凭据或自动新增 rewrite。

交付结果：

1. 新配置默认检查普通 HTTPS 页面；严格 HTTP 与 OpenBao 可逐域名指定。
2. 多个域名组成一个共享候选 IP 的组，由一个主域名排名，全部成员复验通过后才可切换。
3. 旧配置和旧状态继续可用；新配置、报告和状态有明确版本与迁移边界。
4. 只读 probe、dry-run 与实际写入能够逐组、逐域名说明结果，部分更新故障可恢复且不会覆盖人工修改。

## 配置模型

### 版本与归属

- 未声明 schemaVersion 的文件按现有 v1 规则处理，省略 healthMode 仍是 openbao；旧 http 的内容标记仍必填。显式 schemaVersion: 1 也使用相同语义。
- schemaVersion: 2 才启用本文模型。未知版本、未知字段、null、混用旧顶层 domain/healthMode 与 groups 均报错。
- 全局保留现有候选、采样、超时、对照 DNS、AdGuard Home 地址和凭据加载配置；不复制一套嵌套全局配置。不支持组级覆盖这些参数。
- groups 是非空数组，首阶段每份配置最多 **16 个域名、4 个组、每组 8 个成员**，三个硬上限同时生效。主域名也是组内成员，只计一次；域名总数为全部组的成员数之和。组 id 唯一且稳定，限制为 1..64 个小写字母、数字、连字符，首字符为字母或数字。
- 上限由程序固定，不提供无限制选项。启动时先校验整份配置，超限明确报告实际数量、允许上限和对应组（如适用），不截断、不跳过成员；指定 --group 也不能绕过未选中组或全局总数的校验。
- 每组 primary 指向一个成员 domain；members 是非空数组。一个规范化后的域名只能出现在一个组中，避免互相改写。
- domain 沿用现有 ASCII DNS 名校验，大小写统一，并对末尾单个点规范化后去重；不接受 IP、通配符或 URL。国际化域名须提供 ASCII 形式。
- 每个成员以 url 为唯一的协议、端口和路径来源；必须是 https、有效端口 443（省略即 443），hostname 与 domain 相同。拒绝 userinfo、fragment、反斜杠及控制字符；查询参数允许但不得含秘密。domain 用于 rewrite 身份，url 用于具体检查，不另设 healthPath/port。
- mode 默认为 https，可选 http 或 openbao；不自动识别模式或在失败时降级。
- v2 stateFile 必须显式填写，与 v1 分开。只有 run 使用状态；probe 不要求存在状态文件，也不读取 AdGuard 凭据之外的业务凭据。

上述数量是首阶段的维护与运行预算选择，不是已测得的技术极限：总数限制整轮成本，组数限制独立排名次数，单组大小限制共享候选复验和部分写入失败后的恢复范围。域名上限不能替代请求数和运行时间限制，三者同时生效。后续只有出现真实使用需求并取得测量及恢复测试数据后，才评估调整上限。

以下是格式 2 的只读配置，候选路径相对配置文件所在目录；对应可解析示例为 `config.groups.example.json`（源码在 `examples/`，部署包在根目录），使用前替换实际域名。固定目录部署改用 `config.groups.run.example.json`，路径对应见 [DEPLOY.md](../DEPLOY.md#目录与模板选择)：

```json
{
  "schemaVersion": 2,
  "candidateFile": "candidates/cloudflare-ipv4.txt",
  "cloudflareRangesFile": "candidates/cloudflare-ipv4.txt",
  "candidateSources": [],
  "stateFile": "state/optimizer-v2.json",
  "maxRequestsPerGroup": 160,
  "maxRunSeconds": 1800,
  "groups": [
    {
      "id": "personal-sites",
      "primary": "www.example.com",
      "members": [
        {
          "domain": "www.example.com",
          "url": "https://www.example.com/"
        },
        {
          "domain": "files.example.com",
          "url": "https://files.example.com/ready",
          "mode": "http",
          "expectedStatusCodes": [200],
          "expectedBodyContains": "service-ready"
        },
        {
          "domain": "bao.example.com",
          "url": "https://bao.example.com/v1/sys/health",
          "mode": "openbao"
        }
      ]
    }
  ]
}
```

run 另需现有 adguardHomeUrl、adguardHomeDns 和独立 .env 凭据。无后端时 probe 可运行，run/dry-run 给出缺少配置的错误。首阶段所有组共用一个 AdGuard Home 实例，不引入未来 hosts 后端的占位配置。

### 三种探测模式

| mode | 默认判定 | 响应读取 | 可证明的结果 |
| --- | --- | --- | --- |
| https（v2 默认） | 正常 TLS，最终 2xx，无已识别挑战信号 | 只读至 maxResponseBytes 的前缀后关闭；大页面不因超限失败 | 此 URL 的基本 HTTPS 响应可用，不保证业务健康 |
| http（显式） | 必填预期 2xx 状态码；内容标记可选，设置时必须匹配 | 标记仅在限定前缀内查找；不存在则失败且注明检查范围 | 响应符合用户指定条件 |
| openbao（显式） | 沿用当前 JSON、Content-Type、状态码与 initialized/sealed/standby 判断 | 必须在上限内读完整 JSON，超限仍失败 | 专用健康接口的已实现健康语义 |

v2 http 的状态列表范围、数量和内容标记长度限制沿用当前规则；显式空标记报错，省略则只检查状态。https/openbao 不接受 expectedStatusCodes/expectedBodyContains，避免用户以为条件生效。OpenBao standby 仍不代表已经验证业务转发。

所有模式使用 GET、新建连接、HTTP/1.1、正常证书验证；普通页面使用适当 Accept，不强制 application/json。读取前缀不是截断后伪装完整响应，报告记录 bodyTruncated；到上限主动停止与到上限前网络读取失败分开处理。不保存响应正文、Cookie 或完整 Location 到报告。

v2 https/http 最多跟随 3 次同源 HTTPS 重定向，原域名、有效端口和候选 IP 必须保持不变；每跳重新验证，复用同一请求超时预算。跨域（包括跳至 www 别名）、端口变化、HTTP 降级、无效 Location、循环或超限均不自动跟随，不记为合格；提示用户配置最终 URL。OpenBao 及 v1 继续拒绝重定向。

排名使用从首个请求开始到最终响应首字节的时间，包含跳转开销；同时保留每跳状态和耗时，避免将第一个 301 的延迟当作最终页面成绩。读取失败仍使样本不合格。

403、429、5xx、证书错误及已识别的 Cloudflare 挑战分别分类，不因 TLS 成功就算合格。挑战识别不能覆盖所有自定义页面；普通 200 登录页或未知挑战可能只得到“基本响应可用”。报告必须保留这个保证级别，不将其称为业务健康。需要更强判断的用户选择 http 内容标记或 openbao，不把默认模式变成 HTML 内容猜测器。

## 域名组测量与选择

1. 配置校验一次完成；候选源每次执行按原缓存策略加载一次，各组选址独立，默认按配置顺序串行运行。
2. 对主域名进行现有 TCP 初筛与交错 HTTPS 采样。每组重新测量，不跨组复用性能成绩；主域名的排名不能称为组内所有站点的性能排名。
3. run 读取每个成员现有规则，分别确认 DNS；保留每个成员自己的旧 IP。主域名当前 IP 必须进入完整排名，其余成员当前 IP 按各自规则进行可用性复测，不受用户 pinnedIps 的数量限制挤出。
4. 按主域名合格排名，最多取前 3 个地址，依序对所有成员（包括主域名）各做 2 次复验，两次均通过才成为本轮组建议。任意成员失败即淘汰该地址；不跳过成员，也不无限扩大搜索。无共享候选则保留整组原状。
5. streak 以“本轮全部成员复验通过的同一候选”为准，沿用连续确认间隔、改善门槛和冷却。改善比较以主域名当前 IP 为基准；组员复验只保证基本兼容，不声称其他成员延迟改善。无更好主域名候选时，不单独以某个组员失败触发紧急切换。
6. 允许组员旧 IP 不同。若共享候选等于主域名当前 IP、但有组员不同，则标记为“组内对齐”，不虚构性能改善；仍须连续确认、冷却、全部复验及 dry-run 清晰展示。这是用户将域名加入共享 IP 组的配置语义。
7. 达到切换条件后，写前再对所有成员在该 IP 各检查一次，并重新核对整组规则；任何失败或人工改动都取消此次写入。

成员不同意共享候选的常见处理是调整实际检查 URL/规则，或拆为独立组。不得通过静默降低模式、放宽状态码或跳过失败成员来强行切换。

### 请求与时间预算

v2 新增 maxRequestsPerGroup（默认 160，范围 1..1000），限制每组正常测量及写前验证的 HTTP 请求；重定向每跳算一次，TCP 初筛仍受现有 maxCandidates/concurrency/timeout 限制。预算包含当前成员检查、主域名采样、候选复验、写前复验，不只计算最终成功请求。

设成员数 D、实际参与主域名 HTTPS 排名的地址数 F（含对照/保留地址）、samplesPerIp 为 S，忽略跳转时，正常阶段保守预算为 F×S + D + 3×D×2 + D。以 F=13、S=5、D=3 为例，上限为 89 次，跳转另计。实现需根据实际地址数量预估并输出预算；不足时停止，报告 budget-exhausted，不产生本轮确认或写入。

新增 maxRunSeconds（默认 1800，范围 60..7200）限制正常执行阶段，包含候选下载、排队间隔和全部选中组。耗尽时未完成的组不得使用旧结果当本轮成绩。部分组已经完成的结果如实保留。

已开始写入后的核对与恢复不能被普通测量预算切断：单独使用最多 120 秒的恢复上下文，逐成员最多 2 次 HTTPS 校验（新、旧各一次；每次仍受跳转上限约束），API/DNS 核对也有明确超时。无法完成则持久保存 pending，下次先恢复。报告分别列出测量和恢复用量；总运行时间可能比 maxRunSeconds 多最多 120 秒，部署文档应相应设置 service 超时。

## 多域名写入与恢复

AdGuard Home 多条 rewrite 没有组事务；本方案提供逐条日志与条件补偿，不宣称原子切换。

- 写前检查全部成员各有且仅有一条现有、启用的 IPv4 rewrite，且 AdGuard DNS 确认应用。缺失、冲突、CNAME、禁用或解析不符时整组不写，不自动新增、删除或启用规则。
- 在第一条写入前持久化整组 pending，保存事务标识、配置指纹、每条原始规则、目标规则和进度。每次写入前重读该成员；写后回读并保存进度。旧 IP 已等于新 IP 的成员记录为 unchanged。
- 请求超时不代表未提交，必须读取实际规则判定；进程崩溃后即使进度未保存，也可依 old/next/实际值恢复，不盲目重发 PUT。
- 完成后逐成员回读规则、查询指定 AdGuard DNS、经解析所得地址执行 HTTPS 验证；核对实际连接 IP，不能只用固定候选探测替代 DNS 生效验收。
- 任一更新或写后验证失败，停止继续更新，对已改成员逆序尝试补偿。只有实际规则仍等于本次 next，且该成员旧 IP 即时复验通过时才恢复其 old。人工改动不覆盖；旧地址不健康时不盲目恢复。
- 未完全回滚时报告 partial/recovery-required 和逐成员 old/next/actual，保留 pending。未完成事务阻止新的自动更新；同一状态文件内先处理 pending，再开始任何组的测量与写入。
- dry-run 只报告 pending 及拟恢复动作，不修改 DNS，也不推进确认、冷却或事务状态。
- 组之间不建立事务。普通无合格候选可继续下一组；认证失败、状态持久化失败、未解决 pending 等影响安全写入的问题停止整个 run。不得以某组成功掩盖其他组失败。

保留现有运行锁。v2 同一 AdGuard 实例的受管理域名集中在一个配置和状态文件内；拒绝组间重复域名。不同状态文件的锁不能阻止外部写入，仍必须进行重读和条件恢复，并在部署文档禁止多份任务接管相同域名。

## 状态、报告与命令兼容

- v1 配置继续使用原来的 v1 状态及报告形状，不以新默认覆盖旧配置，不自动重写用户文件。
- v2 状态 version 为 2，以组 id 记录观察值、胜出候选、确认次数、冷却、每域名规则、最近 48 轮摘要和 pending。候选原始样本只进入报告，不无限积累于状态；状态读写上限保持 4 MiB，写前校验大小，超限不更新 DNS。
- 配置指纹覆盖主域名、成员集合、URL/模式/预期、采样与选择门槛、AdGuard API/DNS 身份。组成员顺序不影响指纹；实质变化或人工规则变更清空连续确认，已有冷却不得因改配置绕过。有 pending 时禁止按新指纹执行，需以原配置先恢复。
- v2 读取 v1 状态时明确拒绝并提示新建 stateFile，不能自动迁移未完成事务。迁移须先用旧配置处理 pending，再另存 v2 配置/状态；旧文件保留用于退回。退回时重新读取实际规则，不能把旧快照当作当前值。
- 新增 --group <id> 用于 probe/run/dry-run，默认全部组；未知组失败。refresh/export 仍为全局候选操作，不接受组筛选。处理 pending 优先于组筛选，不得用筛选跳过恢复。
- v2 报告含 schemaVersion、groups、overallStatus；组结果含 primary、排名、组建议、各成员检查、预算、变更原因、逐条写入与恢复结果。明确区分主域名建议与通过全组复验的建议。
- 退出码：全部选中组正常完成为 0（无需切换也是正常）；无合格共享候选或测量预算耗尽为 2；配置/IO/API/写入/恢复错误为 1。多组取错误优先级 1 > 2 > 0，始终保存已取得的逐组结果；报告写入本身失败则输出可操作错误。

迁移文档必须说明旧 http 与新 http 的差别；迁移示例保留已有内容标记，不借迁移降低健康保证。新默认仅对 v2 新配置生效。
